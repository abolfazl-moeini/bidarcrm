## Pillar 1: Core Testing Internals

**HposTestCase / HPOSToggleTrait are real, but narrower than implied.** They exist in `woocommerce/woocommerce` core, introduced alongside HPOS sync testing — `DataSynchronizerTests` and `OrdersTableDataStoreTests` were consolidated to inherit from a common `HposTestCase` class, with the toggle helper renamed to `HPOSToggleTrait` for clarity. They're core-internal test scaffolding for exercising sync between the posts table and the new orders tables — not a documented, stable public API that third-party plugins are expected to extend. If your `wc-core-test` v2 wants HPOS/CPT dual-mode support, treat these as inspiration, not an interface contract; core reserves the right to change them without a deprecation cycle since they're `tests/` internals, not `src/`.

**"Fixture Ladder" is not established WooCommerce terminology.** I couldn't find this phrase, nor `MetaDataAssertionTrait`, `LoggerSpyTrait`, or `SerializingCacheTrait`, anywhere in the core repo, developer blog, or community writing. The underlying *concept* you're gesturing at — a spectrum from full `WC_Order` object creation, down to `wc_create_order()`, down to raw table inserts — is a real and useful pattern, but it's not something WooCommerce core names or standardizes. I'd flag this in your report as a concept you're introducing for `wc-core-test` v2, not something you're adopting from upstream.

**The TRUNCATE/rollback antipattern is real and well-documented — but it's general MySQL/MariaDB behavior, not WooCommerce-specific.** `WP_UnitTestCase` wraps each test in a transaction that's rolled back in teardown for isolation. The problem: TRUNCATE TABLE is a DDL-adjacent statement that causes an implicit commit — even if the statement itself later fails, the transaction up to that point is committed and cannot be rolled back. Any legacy WC extension test that runs `TRUNCATE` on a custom table (session tables, lookup tables) mid-test silently breaks the isolation guarantee for every test that runs afterward in that process — a classic source of test order-dependence bugs. This is a legitimate finding to put in your antipatterns audit; just cite it as generic MySQL/MariaDB semantics rather than a WooCommerce-authored warning.

## Pillar 2: Community & Commercial Patterns

Real, current tooling in this space:

- **`level-level/wp-browser-woocommerce`** — actively maintained, gives you a `WCTestCase` you extend instead of wp-browser's `WPTestCase`, which adds WooCommerce-aware factories so you can do `$this->factory()->product->create_and_get(...)` and `$this->factory()->order->create_and_get(...)` with line items. This is the closest thing to a decoupled, Composer-installable WC test-factory package that exists today.
- **`woocommerce/qit-cli`** — this is real and is WooCommerce's own answer to "why isn't there a standalone test framework package." QIT is explicitly built as the official quality gateway for the WooCommerce Marketplace, running standardized checks (security, compatibility, performance, static analysis) with zero setup, plus Playwright E2E in a common format that can combine packages from multiple plugins in one run. But it's a *managed test runner/CI platform*, not a unit-test helper library — it doesn't give you `OrderBuilder`-style factories for your own PHPUnit suite. It does enforce HPOS support as a validation gate — declaring explicit HPOS incompatibility fails the check, which is a strong signal that any 2024+ extension test suite needs HPOS-aware fixtures as table stakes, reinforcing your Pillar 4 goal.
- **`humanmade/woocommerce-demo-generator`** — I found no evidence this package exists under that name/org; likely conflated with Human Made's WP demo-content tooling in general, not a WooCommerce-specific test-fixture generator. Don't cite it as a real dependency without verifying directly against Packagist/GitHub.
- Automattic, YITH, Barn2, WPDesk don't publish their internal test architectures publicly in any detail I could find — this is expected, since it's proprietary CI tooling. Any "how top-tier developers structure tests" claim beyond what's visible in open-source extensions (like WooCommerce Subscriptions, which is source-available) would be speculative.

**Why no standalone `woocommerce/test-framework` package:** the practical answer is that WooCommerce's unit/integration tests are tightly coupled to the monolith's bootstrap (`tests/bin/install.sh`, the wp-tests-lib database, `WP_UnitTestCase`) rather than factored into an independent library — setup still requires spinning up a MySQL test database and running Composer/PHPUnit from inside the `plugins/woocommerce` tree. Decoupling that would mean maintaining a second public API surface, which core hasn't prioritized. The clean workaround used in practice is exactly what `level-level/wp-browser-woocommerce` and QIT do: wrap the existing bootstrap rather than replace it.

## Pillar 3: Hybrid Unit/Integration Model

Brain Monkey + Mockery for true WordPress/WooCommerce-free unit tests is a mature, well-trodden pattern: Brain Monkey provides WordPress-specific mocking utilities that make unit testing WordPress extensions straightforward without booting WordPress, and the standard setup wraps `Brain\Monkey\setUp()`/`tearDown()` in your base TestCase's `setUp()`/`tearDown()`. The line for what belongs where is fairly consistent across the community: pure business logic, calculation, and formatting (discount math, string builders, small data transforms) → Brain Monkey; anything touching real `WC_Order`/`WC_Product` persistence, hooks firing in sequence, HPOS data-store behavior, or meta CRUD → real `WP_UnitTestCase` integration tests against MySQL. Worth noting for your v2 design: `pfaciana/brain-monkey-doubles` is a newer package (actively pushed as of mid-2026) that fills two real gaps in vanilla Brain Monkey — letting you both stub a function's return value and still assert it was called with specific arguments, and making registered `add_filter`/`add_action` callbacks actually execute during a test instead of just being recorded. That second point directly solves your "sessions/cart/notices throw null errors" problem — a lot of the friction there is that `WC()->session`, `WC()->cart`, and `wc_add_notice()` rely on hooks and singletons that never got initialized in a headless mock environment; either Brain Monkey Doubles' real-hook-execution model or a thin `WC()` container stub (returning fake session/cart doubles) resolves it without booting MySQL.

## Pillar 4: v2.0 Architecture Recommendation

Given the above, a defensible v2 design:

1. **Fluent builders over statics** — your instinct here is sound and matches where the ecosystem is heading (level-level's factory pattern is the closest real precedent, though it's array-based rather than fluent-chained).
2. **HPOS/CPT dual support** — implement it as a constructor-injected data-store flag or a `usesHpos()` trait method your builder checks, rather than modeling directly on `HposTestCase`, since that class isn't a stable public contract.
3. **Cleanup** — replace `TRUNCATE` with `DELETE FROM ... WHERE` scoped to IDs your factory created, tracked in an array and cleaned in `tearDown()`; this preserves `WP_UnitTestCase`'s transaction rollback instead of defeating it.
4. **Toolchain** — `declare(strict_types=1)`, PHP 7.4–8.3 via conditional syntax or a Rector-based dual-build, PHPUnit 9.x with the Yoast/`php-compat` polyfills for `assertMatchesRegularExpression`-style API drift.
